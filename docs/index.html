Documentation

Tallow Copy

A native copy engine in Rust, a CLI that drives it, and a desktop app built on both. One implementation of byte movement, content hashing and the skip/verify verdicts is shared by the CLI, the Tallow scripting surface and the app — so “the bytes arrived” cannot differ between them.

MIT licensed · engine depends only on blake3, filetime, libc

Install Download View on GitHub

  • One verdict, three surfaces

    The CLI, the .tl scripting surface and the desktop app share a single implementation of byte movement, hashing and the skip/verify verdicts. The docs record a lazy-hash defect that once shipped in two copies at the same time and had to be fixed twice — which is why the duplication was removed.

  • Stateless by default

    The engine is standalone by design — blake3, filetime and libc, nothing from the wider tallow crate. Copying is recursive and read-only on the source.

  • Verification, not trust

    verify-transfer compares without writing; manifests let a machine that never had the source check a copy; audit-transfers shows the log. An audit compares — it never writes.

  • Parallelism derived, not assumed

    The worker count is derived from the tree and the path class, not the core count. Measured: on a CIFS target, 8 threads was about 26% slower than 1. -j 0 asks the engine to choose.

01

Install

The desktop app is a webview app: WebKitGTK on Linux, WebView2 on Windows (present on Windows 10+), WKWebView on macOS. On Linux the deb declares exactly two dependencies — libwebkit2gtk-4.1-0 and libgtk-3-0 — and apt resolves them for you. The engine has no system dependencies at all.

The deb — Debian / Ubuntu

shell
sudo apt install ./tallow-copy_0.1.0_amd64.deb

Download: tallow-copy_0.1.0_amd64.deb (3.2 MB)

Or, if you prefer: sudo dpkg -i followed by sudo apt -f install. Installing from a local path with apt is what pulls the dependencies in.

Not for Arch-family systems. A .deb is a Debian package; on Arch, use the AppImage or build from source. (Verified the hard way: this project’s own machine is CachyOS and has no dpkg-deb.)

The AppImage — any distribution

shell
chmod +x tallow-copy_0.1.0_amd64.AppImage
./tallow-copy_0.1.0_amd64.AppImage

Download: tallow-copy_0.1.0_amd64.AppImage (77.7 MB)

One file, no install, no dependencies to resolve. If the host lacks FUSE, run it with APPIMAGE_EXTRACT_AND_RUN=1 ./tallow-copy_0.1.0_amd64.AppImage.

macOS — CI artifact, unsigned

Download: tallow-copy_0.1.0_x64.dmg (3.0 MB)  ·  tallow-copy_0.1.0_aarch64.dmg (3.0 MB)

Built by CI from the same sources, and unsigned. macOS needs the quarantine attribute cleared, or a right-click Open:

shell
xattr -dr com.apple.quarantine "Tallow Copy.app"

Windows — CI artifact, unsigned

Download: tallow-copy_0.1.0_x64_en-US.msi (3.1 MB)  ·  tallow-copy_0.1.0_x64-setup.exe (2.0 MB)

Built by CI from the same sources, and unsigned. Windows shows a SmartScreen warning; accept it to run.

Proper signing needs a code-signing certificate and an Apple Developer ID; until those exist these are artifacts you can run after accepting the warning, and nothing more should be claimed for them.

Build from source

Prerequisites: a stable Rust toolchain, Node 20 for the app, and on Linux the development packages libwebkit2gtk-4.1-dev, libgtk-3-dev, libfuse2 and patchelf.

Engine and CLI-side use:

shell
cargo build --release -p tallow-copy-engine

The desktop app:

shell
cd apps/tallow-copy
npm ci
npm run build
npx tauri build

Building the AppImage with Tauri’s own invocation fails with failed to run linuxdeploy. That is a packaging-tool defect, not a problem with the application: Tauri pins a linuxdeploy whose bundled strip cannot read .relr.dyn sections that modern system libraries use. A current linuxdeploy handles them, so the bundle succeeds when that one is invoked directly against the staged AppDir, with the plugin directory pointed at Tauri’s downloads. The deb path is unaffected.

Headless servers — use the CLI

A server wants the engine, not the window. Copy the tallow binary plus your .tl scripts and you have the same engine: tallow copy, tallow delta-sync, tallow verify-transfer, tallow manifest-create, tallow manifest-verify. This is how the project’s own nightly 45 GB NAS push runs — a .tl script driven by a timer.

02

Command reference

Every command below is Tallow Copy’s, verified against the live binary. Run them from a checkout of the repo, or replace cargo run --quiet --bin tallow -- with an installed tallow binary.

tallow copy

Copy missing or changed source entries to a destination. Recursive. Read-only on the source.

syntax
tallow copy <SRC> <DST>

Example

shell
tallow copy /srv/data /mnt/backup/data

Flags

--resume
Continue each interrupted file from its deterministic partial sibling. Local paths only.
-q, --quiet
Suppress all non-error output.
-v, --verbose
Verbose output.
--no-color
Disable coloured output (env NO_COLOR).

The partial sibling is .name.tallow-partial beside the destination, which a resume run deliberately leaves behind on failure. A finished destination makes any partial stale, so it is ignored rather than spliced in.

tallow delta-sync

Delta sync between directories. This is the stateful one-way reconciler (it keeps SQLite state to decide what changed); it is a different capability from the stateless copier above.

syntax
tallow delta-sync <SRC> <DST>

Flags

-j 0
Ask the engine to choose the worker count. Thread count is derived from the tree and the path class rather than the core count. Measured: on a CIFS target, 8 threads was about 26% slower than 1, and on large local files 8 threads managed 581 MiB/s against 3556 MiB/s for a single thread.

tallow verify-transfer

Compare a target against a source, read-only, and report what is missing, what differs and what is extra. Nothing is written.

syntax
tallow verify-transfer --source <SOURCE> --target <TARGET> [--verify <MODE>] [--json]

Example

shell
tallow verify-transfer --source /srv/data --target /mnt/backup/data --verify hash

Flags

--verify size
Default. Size + mtime, cheap.
--verify hash
Confirms matches by reading both sides.
--verify hash-all
Hashes regardless of size and mtime.
--json
Machine-readable report.
--limit <N>
Cap listed differing paths (default 50).

Choose size for “did the bytes arrive intact” and hash when it actually matters. A same-length file whose mtime was preserved is reported as in sync under size and as a difference under hash — measured, not asserted.

tallow manifest-create

Write a manifest of a tree — relative path, size and content hash per file — so a copy can be verified later on a machine that never had the source.

syntax
tallow manifest-create ...

Format: path<TAB>size<TAB>blake3 behind a version header (# nixe manifest v1), deliberately plain TSV: a manifest is read by humans during an incident and by scripts afterwards.

tallow manifest-verify

Verify a tree against a manifest written by manifest-create.

syntax
tallow manifest-verify --manifest <MANIFEST> <ROOT>

extra entries are reported and never deleted: a manifest records what was sent and is not an authority to remove anything.

tallow audit-transfers

Show the transfer audit log.

tallow hash

Hash a file with BLAKE3.

From a Tallow script (.tl)

The same engine is reachable from the scripting surface:

.tl
Transfer.manifest_create(root, out) -> i64
Transfer.manifest_check(root, manifest) -> String   // JSON report
Transfer.hash(path)

Not Tallow Copy. The wider Tallow toolkit also ships relay, speed-test, two-way-sync and watch. They belong to the broader TallowTransfer work, not to this engine. Do not present them as Tallow Copy features.

Benchmarks

Every number here was measured on one Linux workstation and its own storage and network. They are provenance, not marketing: treat them as “what this machine did”, not as portable claims. The project’s benchmark protocol explicitly forbids throughput claims against other tools until a harness produces that data, so none appear here.

Engine performance smoke (tiny dataset)

A dedicated test:

shell
cargo test -p tallow-copy-engine --test perf_copy_engine -- --ignored --nocapture
Engine performance smoke results
Files9
Logical bytes33,587,200  (32 MiB)
Copy59 ms
Verify28 ms  (inside copy)
Throughput542.9 MB/s
Warm passskipped 9, verified 9

The dataset is tiny, so read this as “the plumbing works and is not slow”, not as a peak number. The warm pass skipping all nine files is the skip policy doing its job.

Network targets

CIFS/SMB NAS over Wi-Fi (1040 Mbit/s PHY): write 43.6 MB/s, read 50.9–55.3 MB/s.

CIFS throughput by number of concurrent streams
Concurrent streams1234
Throughput47.2 MB/s45.2 MB/s35.1 MB/s38.4 MB/s

No parallel scaling on this target, and four streams are worse than one. The protocol records that as an acceptance gate: a target that does not scale should be recognised, not fought.

WAN over SSH, RTT 133.71 ms: 13.27 MB/s single stream, 25.20 MB/s at two streams (1.90×), with a ceiling of roughly 201 Mbit/s reached at two. A third stream adds nothing.

Thread counts, and why they are derived

Measured throughput by thread count and workload

Local small files440 MiB/s801 MiB/s868 MiB/s

Parallelism helps many small files and actively hurts large sequential ones. That is why the engine derives the worker count from the tree and the path class instead of using the core count, and why -j 0 asks it to choose.

04

Troubleshooting and FAQ

These are problems this project actually hit, with the fix that worked.

failed to run linuxdeploy while bundling the AppImage

Tauri’s pinned linuxdeploy aborts inside its own strip, which cannot read .relr.dyn sections used by modern system libraries. linuxdeploy --version runs fine and libfuse2 is present, so it is neither FUSE nor a failure to start. Use a current linuxdeploy directly against the staged AppDir, with the plugin directory pointed at Tauri’s downloads. Building the .deb is unaffected.

The visual test suite dies before any page loads

Error: browserType.launch: Executable doesn't exist at .../chrome-headless-shell. The configured browser directory exists and even contains the right revision folder — the executable inside it does not. The suite now resolves the browser by looking for a runnable binary (vendored path, then ~/.cache/ms-playwright) and leaves PLAYWRIGHT_BROWSERS_PATH unset if neither can launch, so Playwright reports its own error. Set PLAYWRIGHT_BROWSERS_PATH explicitly to override.

The .deb will not install

It is a Debian package. On Arch-family distributions there is no dpkg to install it with — use the AppImage or build from source.

tallow: command not found

The binary is not installed to your PATH by default. Either run it from the checkout (cargo run --quiet --bin tallow -- copy src dst) or install a release build into ~/.local/bin.

The desktop app does not start on a server

It needs a display; it is a desktop window, not a service. Use the CLI on headless machines — it drives the same engine.

“a manifest is needed” when verifying

Manifest verification requires a manifest. The plan checks for one up front, names what is missing, and reads and parses it before the transfer starts, so a bad manifest fails before any bytes move rather than after.

Why does verify-transfer say “in sync” when a file changed?

You are using the default size policy, which compares size and mtime. A same-length file with a preserved timestamp is indistinguishable to it. Use --verify hash, which reads both sides. This is measured, not theoretical — with the size policy a tampered file whose mtime was reset reports “in sync”, and with --verify hash the same tree reports one difference.

Mirror deletes were refused

Destructive mirror operations require an explicit plan review before they execute. Independently, a path that an exclusion filtered out is never deleted — mirror does not delete what it never considered.

Where do settings, history and logs live?

~/.local/share/Tallow Copy/, with logs in a logs/ subdirectory and finished jobs in history.json beside them. History is written from terminal job states only, so a job that failed halfway cannot be filed as complete. Copy that directory to carry your configuration to another machine.

Are the macOS and Windows builds signed?

No. See Install — expect a SmartScreen warning on Windows and a quarantine attribute to clear on macOS.

Advanced usage

Real jobs, assembled from the commands above. Every flag and number on this page is documented in the command reference and the benchmarks.

The nightly NAS push

The project’s own 45 GB NAS push runs headless: a .tl script driven by a timer, with the tallow binary and the scripts copied onto the machine. The whole surface — copy, delta-sync, verify-transfer, manifest-create, manifest-verify — is available without the app.

syntax
tallow delta-sync <SRC> <DST>

-j 0 asks the engine to derive the worker count. Measured: on a CIFS target, 8 threads was about 26% slower than 1 — which is exactly why the count is derived from the tree and the path class instead of assumed from the core count.

Copy, then prove it landed

shell
tallow copy /srv/data /mnt/backup/data
tallow verify-transfer --source /srv/data --target /mnt/backup/data --verify hash

Choose size for “did the bytes arrive intact” and hash when it actually matters. Finish by checking the audit log: tallow audit-transfers.

Resume an interrupted copy

shell
tallow copy /srv/data /mnt/backup/data --resume

Each interrupted file continues from its deterministic partial sibling (.name.tallow-partial beside the destination), which a resume run deliberately leaves behind on failure. Local paths only: a finished destination makes any partial stale, so it is ignored rather than spliced in.

Ship a tree to a machine that never saw the source

syntax
tallow manifest-create ...
tallow manifest-verify --manifest <MANIFEST> <ROOT>

Create the manifest beside the tree, transfer both, then verify on arrival. The manifest is plain TSV (path<TAB>size<TAB>blake3 behind a version header) — readable by humans during an incident and by scripts afterwards. extra entries are reported and never deleted. The same engine is reachable from a script: Transfer.manifest_create(root, out), Transfer.manifest_check(root, manifest), Transfer.hash(path).

06

Changelog

2026-10-09 · parity, publishing and CI

The app stopped guessing. The worker count shown as “AUTO” was a literal 16 rather than a derivation; it now asks the engine, and one function owns that rule so the number the engine uses and the number the interface shows cannot disagree. Resume became reachable for plain copies, a fail-fast error policy became selectable, and the engine’s small-file bundling advice now travels to the interface through warnings it already rendered.

The app can answer “did it land?”. The tree audit moved into the engine and the standard library now delegates to it, removing about sixty lines of duplicated counting. The desktop app gained a read-only Verify action with a report. An audit compares; it never writes.

Manifest verification does what its name says. It previously refused rather than silently degrade to a hash. Now a manifest is required, validated before the transfer, and the finished result is checked once; a mismatch names the file. Scripts gained Transfer.manifest_create and Transfer.manifest_check, so a script no longer reimplements the format.

Job history survives a restart. Finished jobs are persisted beside the logs, written from what the interface observed.

Publishing. MIT licence text added for the workspace and the engine crate. The engine was verified to package and compile standalone. CI builds all four targets — Linux deb and AppImage, Windows MSI and NSIS, macOS app and dmg for both architectures.

Fixes. The visual test suite ran against a browser install that could not launch. The empty review queue said “Nothing needs review” directly beneath an audit report that had just found differences; it now speaks only for the queue. Two specification documents were corrected after the work above made them stale — the engine architecture doc still called manifest verification refused, and the app README still listed resume and sampled-hash verification as absent.

Contributing

Layout

  • crates/tallow-copy-engine/ — the engine. Standalone by design: blake3, filetime and libc, and it must not depend on the wider tallow crate.
  • apps/tallow-copy/ — the Tauri desktop app.
  • docs/ — architecture, the benchmark protocol, and the audit records.

Fork and branch

shell
git clone https://github.com/aamirmanisa/tallow-copy
cd tallow-copy
git checkout -b fix/short-description

Use a descriptive branch name; the project’s history reads as a sequence of decisions, so branch names and commit messages are part of the documentation.

Before you open a pull request

shell
cargo test -p tallow-copy-engine
cd apps/tallow-copy && npm ci && npm run test:visual

The engine tests are the contract for planning, copying, verification and the manifest. The visual suite renders the interface in a real browser and asserts layout, which catches the class of regression that unit tests cannot.

Commits and pull requests

Explain the reason, not just the change. If a fix corrects a specification or a comment that had become untrue, say so. If a number appears in a commit message, it should have been measured — the project’s benchmark protocol exists precisely so that claims are reproducible.

In the pull request, state what you ran and what it returned. “Tests pass” is weaker than the command and its result.

What CI does

.github/workflows/tallow-copy-build.yml builds every platform on its own runner: Ubuntu for the deb and AppImage, Windows for MSI and NSIS, and both macOS runners for the app and dmg. Tauri cannot produce Windows or macOS bundles from Linux, and the runners are how each platform’s build is verified rather than assumed. Artifacts are uploaded per platform.
